## 当天概览

白天主要纠偏"旅行足迹"产品的开发流程——main agent 用错工具链路导致生成两套不可用的代码。晚上转向 ClawSwarm 研究，经过反复阅读源码后决定安装部署群聊模式。

## 有价值的收获

- **重新确认了 sage、coder、writer 是独立 Agent（非 ephemeral subagent）**：修正了此前对自身配置的认知错误，直接影响 ClawSwarm 方案的必要性判断和群聊模式适用范围。
- **ClawSwarm 群聊对单机单实例的配置门槛很低**：只需安装 clawswarm channel 插件并注册为 channel，scheduler-server 是可选项。
- **ClawSwarm 群聊的消息路由策略可细到 agent 级别**：支持 round-robin / all-reply / moderator 三种模式，moderator 下可指定某个 agent 做唯一回复者。

## 问题或风险

- **main agent 多次不先查阅已有文档就回答用户**：技术栈已写入需求文档却重问、未查配置就判断 agent 类型、对 ClawSwarm 仅看文档表面就下结论——每次都需要用户纠正，来回沟通成本过高。
- **开发工具调错导致代码浪费**：coder subagent 生成了不符合规范（非 Gin 框架、含编译二进制）的代码，而正确的 Claude Code 链路又没用上，两套代码都不能直接用。

## 可复用经验

- 对不熟悉的组件，不应仅凭 README 或搜索引擎结果回答，应直接读源码做判断——今天 ClawSwarm 的最终准确结论全部来自源码阅读。
- 回答产品/项目相关问题时，main agent 必须先读取产品目录下的现有文档再回复，避免反复问已决事项。
- `sprint dev → Claude Code CLI` 是明确的开发链路，不走内部 coder subagent；下次在 sprint dev 阶段就写清楚"通过 claude CLI 外挂执行"。
