## 当天概览

今天的主要精力都放在了旅行足迹系统的迭代交付上。我先是梳理了 Sprint 2 的三个功能点，确认目标后让助手完成开发、部署和上线，最后关闭了迭代。过程中发现产品迭代脚本底座有几个不够顺手的地方，借这个机会我决定顺手修一修——让助手排查重复调度的问题、精简了状态文件的结构、优化了迭代报告的排版方式。忙里偷闲，还记了一条关于投资的小感悟。

## 有价值的收获

- **工作目录的边界设定要够具体**。原本 `workingDir` 指向的是 `gitRoot` 父目录，coder agent 能访问所有项目，边界太模糊。我让助手直接改成具体项目目录，后续开发隔离更清晰、操作也更安全。

- **父进程被杀不等于子进程也停了**。这次调度重复的根因是 exec 超时后父进程被 kill，但底层的 coder agent 子进程没跟着一起终止，还在后台继续跑到完成。这个盲区之前完全没意识到，排查后才看清楚。

- **`appendToHeading` 没有幂等保护是一个经典陷阱**。脚本每次调用 `sprintReport` 都会无条件追加日志，不做去重。一旦重复调度，日志就翻倍了。这个问题暴露出来后，我让助手在状态文件里加了执行标记来防止重复调度，虽然日志去重的修复还没做，但至少先堵住了入口。

- **状态文件的字段设计要轻量**。之前 `lastResult` 存了一大套完整执行摘要，实际上只被用来判断"跑没跑完"这一个布尔场景。我决定换成纯粹的 `lastCompleted: true/false`，干净多了。

- **报告内容集中到一个日期块里更好读**。我让助手把原本分散在 `验证记录`、`当前阻塞/风险`、`开发日志` 三个独立章节的内容，统一聚合到同一个日期标题下面，阅读顺序自然、不散乱。

## 问题或风险

- **子进程清理机制缺失**。`runOpenClawAgent` 没有在父进程被杀时级联清理子 agent 的逻辑，这是重复调度问题的技术根源，目前还没有修复方案。

- **日志去重仍是个待解问题**。`appendToHeading` 不做同日期去重的检查，这次虽然加了调度入口保护，但如果有其他入口绕过保护直接调用 `sprintReport`，重复日志依然会出现。

## 可复用经验

- **`startedAt` + `lastCompleted` 的双标记模式**很适合做一次性执行守卫——一个记录"什么时候开始的"，一个标记"跑完了没"，两者配合就能精准拦截重复调度。这个模式可以在其他一次性脚本里复用。

- **报告内容按日期聚合优于分散章节**。把执行摘要、功能点、文件变更、验证结果、风险点统一放在同一个日期标题下，比拆成几个独立章节更好读，也方便后续按时间回溯。
