- 我重新校准了 LLMWiki 日报提示词的真实来源，确认应以工作区脚本底座和实际执行链路为准，而不是被其他仓库副本误导；这让我后续排查和改造时有了更可靠的依据。
- 我明确修正了日报的叙述视角，把输出从第三方旁观改成第一人称回顾；这让日报更适合我自己阅读和复盘。
- 我把工作流排查方法进一步固化为“先走执行链路倒推，再定位实际文件”，并确认工作区 `scripts/` 才是运行时权威来源；这能减少因副本、旧仓库或相似目录带来的误判。
- 我对产品迭代工作流的主流程控制权有了更清晰的判断：相比让 Claude Code 参与主流程，我更倾向于把流程完全收回到 OpenClaw 内部，以降低失控和混乱感。

- 我再次验证了“先出方案、确认后执行”不是沟通偏好，而是避免误改、误写、误恢复的重要约束。

## 问题或风险

- 我曾错误读取了 `gitRoot/openclaw-workflow` 下的副本脚本，而不是工作区真实脚本底座；这说明如果不先追执行链路，就容易把相似仓库误当成权威来源。
- 我发现日报历史内容确实曾被改写，并且需要通过恢复方案处理；这说明一旦涉及已有产物的改造或迁移，就存在直接影响历史结果的风险。
- 我确认目前日报文件都堆在 `LLMWiki/daily` 目录下，没有按 `YYYY/MM` 分层存放；这会持续放大后续的管理成本。
- 我也看到产品迭代工作流的职责边界此前并不稳定，尤其是在 Claude Code 是否参与主流程、`sprint dev` 与 `sprint brief` 的定位、上下文分发对象等问题上，相关设计语义仍在收敛过程中。
- 我注意到同一问题在当天记录中出现了重复片段，这说明对话整理或转录层面可能存在重复汇总，后续复盘时容易干扰我判断真正主线。

## 可复用经验

- 我以后排查工作流类问题时，应先按执行链路倒推，而不是按文件名直搜后直接下结论。
- 我以后处理脚本底座时，应始终以工作区 `scripts/` 为运行时权威来源，不与 `gitRoot` 或其他副本混用。

- 我以后只要涉及历史内容、目录迁移或生成逻辑调整，就应先设计恢复方案和基线保护，再推进实施。
