## 当天概览

当天讨论了多 Agent 架构下脚本底座的共享方式。最终确认子 agent 不应直接调用脚本底座，统一由 main agent 代理执行，避免竞态风险、保持架构清晰。

## 有价值的收获

- **多 Agent 脚本底座共享的推荐方案是 "main 代理调度" 而非物理共享**。子 agent 各自有独立的工作区和 Git 仓库，物理迁移 `scripts/` 会破坏 `config.js` 中的相对路径逻辑，导致 state 文件指向错误位置。

- **脚本底座本质是状态管理器，以写操作为主**。diary.js、project-research.js 等脚本都写入同一个 Obsidian Vault 和 state.json。多个 agent 各自直接调用会产生竞态条件。

- **子 agent 职责边界天然不适合管理状态**。sage、writer、coder 的专长是处理内容而非管理状态。统一由 main 调度可确保写入串行化、main 保有全局视图、变更影响范围最小。

- **子 agent 如需脚本底座能力，应通过 sessions_send / sessions_spawn 请求 main 执行**。这保持了架构清晰与状态一致性。

## 问题或风险

无。

## 可复用经验

- **多 Agent 共享写操作资源的判断模式**：判断资源是否共享还是代理调度的关键在于——资源是否以写操作为主（应代理调度），是否会产生竞态（严禁直接共享写权限），子 agent 职责是否天然不适合管理状态（应通过主 agent 转发）。

## 后续建议

- 后续子 agent 如有只读查询需求（如查询课题已有素材），可考虑让 main 暴露轻量只读接口，但仍走 main 转发路径，避免引入新的竞态风险。
