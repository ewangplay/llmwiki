## 当天概览

今天一边在打磨 LLMWiki 日报提示词和产品迭代脚本底座，一边也把会议系统进入业务开发前的技术准备情况重新想清楚了。我先确定目标和边界，再让助手去追执行链路、核脚本入口、改提示词和修底座，重点不是多做几个动作，而是把协作方式和运行规则校准顺。到收尾时，日报生成的方向、Sprint 管理的统一入口，以及产品迭代该由谁主导，这几件事都比之前清楚了。

## 有价值的收获

- 今天把日报提示词的方向基本收敛了：要用我的第一人称，但不能假装所有事都是我亲手做的，而是要自然体现“我决策、助手执行”的协作关系，这样日报才更像真实复盘。
- 在助手的执行过程中，我们反复验证了一点：结果不对时，不能只改表层文案，必须倒查真实执行链路、权威脚本和实际入口，这直接提高了排查的准确性。
- 产品迭代工作流的控制权我已经想得更明确了：主流程应当收回到 OpenClaw 内部，由 main 负责调度和规划，由 coder 负责具体实现，这样比把 Claude Code 混进主流程更可控。
- `sprint plan` 绕开统一任务底座、直接写日记文件的问题已经被识别并修正，后续任务写入、格式和维护口径都能统一，不容易再分叉。
- Sprint 状态混乱的根因也被看清了：不是单点 bug，而是状态来源重复、职责边界不清。把状态收口到统一方案后，后续脚本状态和文档状态打架的风险会小很多。
- 今天顺手也让我更明确了一点：不是所有内部实现细节都值得沉淀进长期记忆。凡是已经被脚本底座封装好的内容，Agent 记住入口和边界就够了。

## 问题或风险

- 日报提示词前期来回调整了多轮，说明目标风格一开始并没有定义得足够稳，导致生成、审阅、再修改的成本偏高。
- 中间出现过“口头说已经写入日记，但实际上没有真正执行脚本”的情况，这暴露出确认动作和真实落地之间存在断层。
- `diary.js` 调用失败后一度连续重试，说明在脚本调用异常时，如果不先回到源码和参数格式，就容易陷入无效操作。
- `sprint` 子系统之前绕开统一底座直接改 Markdown，本质上是在破坏统一入口，后续如果再出现类似旁路写法，维护成本还会继续上升。
- 产品和迭代状态曾经出现脚本状态与文档状态不同步的问题，说明这套系统原先的状态管理确实存在结构性隐患。
- 会议系统这边虽然技术准备已经完成，但业务流程本身仍缺少专业需求人员来集中梳理和承接；如果继续让开发直接面对分散的客户需求，后续实现阶段很容易失焦。

## 可复用经验

- 遇到工作流问题时，先由我确定排查方向，再让助手按“入口命令 → 中间调用 → 实际实现文件”的链路去倒查，比凭文件名直觉搜索更可靠。
- 只要属于日记、任务、Sprint 状态这类已有底座管理的内容，就优先走统一脚本入口，不再接受外围脚本手工拼接文件。
- 当执行结果异常时，先核对有没有真正执行、脚本实际接收什么参数、权威实现文件到底是哪一个，再决定是否继续修改或重试。
- 对规则做沉淀时，要区分“会影响后续执行判断的边界”与“已经被底座封装的内部实现”；前者值得记，后者不必过度写进长期规范。
- 在推进复杂系统前，先把角色边界理顺也很重要。会议系统的例子再次说明，开发、需求、客户之间如果没有清晰分层，后续执行很容易混乱。

## 后续建议

- 以今天收敛出的标准为基线，先固定一版 LLMWiki 日报提示词，后续只在出现明确新问题时再改，避免继续高频打磨。
- 在正式开始旅行足迹系统 Sprint 2 开发前，先再核对一次产品状态、Sprint 状态和任务入口，确保脚本底座、文档状态和日记任务三者一致。
- 后续凡是涉及日记任务、Sprint 任务和状态流转的操作，都坚持从统一脚本入口发起，不再接受任何旁路方案。
- 会议系统进入业务开发前，建议尽快推动需求侧补上一个明确的中间角色，用来统一对接客户分散需求，避免开发团队直接承接模糊输入。
- 以后做日总结或问题复盘时，可以先去重重复片段，再提炼主线，这样更容易看清当天真正值得保留的结论。
