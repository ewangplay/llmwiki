## 当天概览

上午完成课题研究脚本的发布控制改造，并修正了 MEMORY.md 的记录习惯。下午围绕旅行足迹系统的图床需求展开多轮技术调研与实操：修复 Immich v2.7.5 升级异常、通过 Tailscale 打通远程访问通道、评估图床方案后最终放弃 Immich，确定本地文件系统 + sharp 的极简方案。傍晚修复了飞书通道的流式 400 报错和插件安全告警。

## 有价值的收获

- **旅行足迹图床方案最终定案**：经过 Immich、飞书转发、Tailscale 等多条路径的对比与验证，最终选择**本地文件系统 + sharp**。核心判断依据——每趟旅行精选约 10 张图，Immich（Postgres + Redis + ML）属于能力严重过剩，文件系统方案零外部依赖、约 50-80 行代码即可实现，彻底消除对 Immich 的耦合风险。
- **MEMORY.md 写入原则得到实质性修正**：通过用户直接指正，确立了"只记录对未来执行决策有实际影响的信息"这一纪律，避免了将一次性开发细节写入长期记忆的习惯性错误。
- **课题发布控制改为 Frontmatter 属性方案落地**：`should_publish`/`publish_title` 写进 define 文件的元数据层，脚本 `finish` 时自动读取，不再依赖 CLI 参数。方案更声明式、心智负担更低。
- **Tailscale 远程访问内网服务的完整链路验证通过**：从安装、授权到手机端联通实测可行，WireGuard 隧道在内网安全审查中很难被拦截，获取了一个可复用的远程访问基础架构。

## 问题或风险

- **飞书场景存在消息不完整发出的沟通摩擦**：用户在飞书写信息时因中途误发送，导致 Agent 基于部分信息做出误判，需要返工，增加了沟通成本。
- **飞书流式卡片在 OpenClaw 上实际不可用**：流式更新与飞书卡片 API 之间存在底层兼容冲突，关闭流式是当前唯一解法，实时反馈体验因此降到"一次性回完整消息"。

## 可复用经验

- **功能开关优先用 Frontmatter 属性承载，而非 CLI 参数**：设定一次后脚本自动读取，修改只需编辑文件，适合课题、博客、发布流水线等场景。对用户来说，可读性和一致性好于记忆命令行参数。
- **Tailscale 作为内网服务远程访问的基准方案**：服务器装客户端、手机装 App，通过分配的 100.x.x.x 内网 IP 直连，免费版足够个人使用，一次配置长期有效。
- **方案选型时先用量级判断工具是否过剩**：图片量小（每趟约 10 张）→ 不要上全量图床系统；外部依赖越大，长期维护成本越高，能用文件系统解决的尽量用文件系统。
